## The setup

Your switch has two kinds of networks:

- **The management network.** `em0` connects to VMM's out-of-band network, which is how you SSH in.
- **The data network.** The `xe-` ports carry real traffic between SW1, SW2, H1 and H2.

Both share **one routing table**, `inet.0`, unless you separate them.

Say your management access was set up with a default route:

```
set routing-options static route 0.0.0.0/0 next-hop 10.x.x.1   <- the management gateway
```

That means: *"For any destination I don't have a more specific route to, send the packet out the management port."* On Day 1, with no routing protocols running, that's harmless. It causes three problems once OSPF or BGP starts.

## Problem 1: Lab traffic disappears into the management port

Later, SW1 needs to reach a prefix that OSPF hasn't learned yet, because a neighbour is down or you've made a config mistake. Without the default route, SW1 would say "no route to host", which is a clear error you can troubleshoot. With it, SW1 matches `0.0.0.0/0` and sends the packet out `em0` to the management gateway. The management network knows nothing about your lab subnets, so the packet is silently dropped.

You'd see ping timeouts instead of an error, and you'd look for an OSPF problem when the real cause is a static route you forgot about.

## Problem 2: The wrong default route wins

In Phase 2–3, your fabric will often learn a real default route from a border device, for example `0.0.0.0/0` through BGP. Now SW1 has two default routes:

| Route | Source | Preference |
| --- | --- | --- |
| 0.0.0.0/0 to the management gateway | Static | **5** |
| 0.0.0.0/0 to the border leaf | BGP | 170 |

Lower preference wins (the table from Day 1), so the **static management route becomes active**. The real fabric default is ignored, and all default-routed traffic heads to the management port and gets dropped.

## Problem 3: The route leaks to your neighbours

A very common config is *"advertise my static routes into OSPF or BGP"*, with an export policy matching `protocol static`. That policy also picks up the management default route. SW1 then advertises "send me your default traffic" to SW2 and everyone else. They all forward unknown traffic to SW1, which pushes it out `em0` into the management network: one bad route breaks the whole lab.

## The two fixes

**Fix 1: a narrow route plus `no-readvertise`.** Route only the subnet you actually manage from, and mark it so it can never be exported:

```
delete routing-options static route 0.0.0.0/0
set routing-options static route 10.20.30.0/24 next-hop 10.x.x.1 no-readvertise
```

Replace `10.20.30.0/24` with your jump host's subnet.
- Problem 1 is solved: unknown lab destinations get "no route" instead of disappearing.
- Problem 2 is solved: there's no competing static default.
- Problem 3 is solved: `no-readvertise` stops any export policy from advertising it.

**Fix 2: a separate management table.**

```
set system management-instance
```

This moves `em0` into its own routing table, `mgmt_junos`. Management routes live there and lab routes stay in `inet.0`, so the two can never interfere. It's the cleaner production approach, but services like NTP and syslog must then be pointed at that instance, so it's slightly more work.

The address after **`to`**, on the line ending in **`via em0.0`**, is your gateway. Here it's `10.49.127.254`.

If this command shows nothing, there's no management default route on that device, so there's nothing to fix. Skip to the check at the end.

## Step 2: Find `<jump-subnet>`

While logged in over SSH:
```
show system users
```

Example output:
```
USER     TTY      FROM              LOGIN@  IDLE WHAT
admin    pts/0    10.49.32.15       9:01AM      - cli
```

The **`FROM`** column is the IP of the machine you're connecting from, your jump host. Here it's `10.49.32.15`.

Turn that into the route. The simplest and safest choice is a host route for just that one machine:
```
10.49.32.15/32
```

If you'd rather cover the whole subnet, log in to the jump host itself and run `ip -4 addr`. It shows something like `10.49.32.15/22`, which means the subnet is `10.49.32.0/22`.

If you also connect from another machine (laptop, VPN), repeat this from that machine and add a second route.

set routing-options static route 10.49.32.15/32 next-hop 10.49.127.254 no-readvertise

To reach my jump host 10.49.32.15, and only that host, send packets to the management gateway 10.49.127.254. Never tell any other router about this route.

It’s a route on the switch, pointing back toward the jump host. It isn’t a route from the jump host. Its job is to let the switch reply to you.


What happens during an SSH session ?

Every SSH session is two-way traffic:

Jump host → SW1: your keystrokes arrive on em0. Delivery works fine: your jump host has its own routes, and the management network carries the packets to SW1.
SW1 → jump host: SW1 must send back the prompt and command output. To do that, SW1 has to look up 10.49.32.15 in its own routing table to decide where to send the reply.

Before, the default route said “reach everything through the management gateway.” Now the static route says “reach only my jump host through the management gateway.”

Fix 1 should be configured or Fix 2 , never both.
